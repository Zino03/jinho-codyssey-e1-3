# Mini NPU 시뮬레이터

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 애플리케이션입니다.
Python 3.8 이상, 표준 라이브러리(`json`, `time` 등)만 사용합니다.

## 실행 방법

```
python main.py
```

실행하면 모드를 고릅니다.

| 선택 | 모드 | 설명 |
|---|---|---|
| 1 | 사용자 입력 (3×3) | 필터 A, B와 패턴을 한 줄씩(공백 구분) 입력하면 점수, 시간, 판정을 출력 |
| 2 | data.json 분석 | `main.py`와 같은 폴더의 `data.json`을 읽어 5×5, 13×13, 25×25 케이스를 일괄 판정 |

### 모드 1 입력 예시

```
필터 A          필터 B          패턴
0 1 0           1 0 1           1 0 1
1 1 1           0 1 0           0 1 0
0 1 0           1 0 1           1 0 1
```

결과: A 점수 1.0, B 점수 5.0, 판정 B. 줄마다 숫자 개수가 3개가 아니거나 숫자가 아니면 안내 문구를 출력하고 해당 행렬을 처음부터 다시 입력받습니다.

### data.json 구조

```json
{
  "filters":  { "size_5": { "cross": [[...]], "x": [[...]] }, "size_13": {...}, "size_25": {...} },
  "patterns": { "size_5_1": { "input": [[...]], "expected": "+" }, ... }
}
```

## 구현 요약

- **MAC 연산** (`mac`): 이중 반복문으로 같은 위치의 값을 곱해 누적합니다. NumPy 등은 쓰지 않습니다.
- **라벨 정규화** (`normalize_label`): 내부 표준 라벨은 `Cross`, `X` 두 가지입니다. expected의 `+`는 Cross, `x`는 X로, 필터 키의 `cross`는 Cross, `x`는 X로 바꿉니다. 대소문자와 공백은 무시합니다. 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.
- **동점 정책** (`judge`): `abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(모드 1은 "판정 불가")로 처리합니다. 동점은 expected와 같을 수 없으므로 모드 2에서는 FAIL입니다.
- **케이스 단위 FAIL 처리**: 키 형식 오류, 필수 항목 누락, 알 수 없는 라벨, 필터 없음, 필터/패턴 크기 불일치, 숫자가 아닌 값은 모두 해당 케이스만 FAIL로 기록합니다. 프로그램은 중단되지 않습니다. 파일이 없거나 JSON이 깨진 경우에는 오류 메시지만 출력하고 돌아옵니다.
- **성능 측정** (`measure_ms`): `time.perf_counter()`로 MAC 호출 구간만 10회 반복 측정해 평균(ms)을 냅니다. 입출력 시간은 포함하지 않습니다.

## 결과 리포트

### 실패 원인 분석

제공된 `data.json`(5×5, 13×13, 25×25 각 2개)의 결과는 **총 6개, 통과 3개, 실패 3개**입니다. 실패한 케이스는 `size_5_1`, `size_13_2`, `size_25_1`입니다.

1. 세 건 모두 점수 계산이나 필터 선택이 틀려서 생긴 실패가 아닙니다. 두 필터의 점수가 수학적으로 같아서 **동점(UNDECIDED)** 이 되었고, 동점은 expected(Cross 또는 X)와 같을 수 없으므로 FAIL이 됩니다.
2. 원인은 필터 가중치입니다. 이 데이터의 필터는 0/1 필터가 아니라 칸마다 값이 다릅니다. 5×5 X 필터는 대각선 칸이 모두 0.1이고 Cross 필터의 중심은 0.9입니다. `size_5_1`(X 패턴)은 Cross 필터와 중심 1칸(0.9)만 겹치고 X 필터와는 9칸(9×0.1)이 겹쳐, 둘 다 0.9가 됩니다.
3. `size_13_2`는 Cross 점수가 7.499999999999997, X 점수가 7.5입니다. `size_25_1`은 Cross 점수가 4.9, X 점수가 4.899999999999999입니다. 이론값은 같은데 소수 덧셈 순서 때문에 1e-15 수준의 오차가 생긴 것입니다.
4. **부동소수점 문제와 epsilon 정책**: 0.1, 0.3, 0.9는 이진수로 정확히 표현되지 않아 누적합에 미세한 오차가 남습니다. `==`나 `>`로 직접 비교하면 오차 때문에 한쪽이 이긴 것처럼 보여 `size_5_1`은 Cross, `size_13_2`는 X로 우연히 판정됩니다. `abs(a-b) < 1e-9`를 쓰면 오차 수준의 차이를 동점으로 일관되게 처리하고, 그 결과 사유가 "동점 규칙"으로 분명히 남습니다.
5. **라벨 정규화**: 이 데이터의 expected는 `+`와 `x`, 필터 키는 `cross`와 `x`입니다. 정규화 없이 판정 결과(`Cross`/`X`)와 비교하면 6건 모두 FAIL이 됩니다. 정규화 덕분에 통과한 3건(`size_5_2`, `size_13_1`, `size_25_2`)이 정상적으로 PASS가 되었습니다.
6. 원인을 세 갈래로 나누면 다음과 같습니다.
   - 데이터/스키마 문제: 라벨 표기 불일치, 키 형식 오류, 필드 누락, 필터와 패턴의 크기 불일치. 이 데이터에는 없고, 정규화와 검증으로 처리합니다.
   - 로직 문제: 점수 차가 충분한데 판정이 expected와 다른 경우. 이 데이터에는 없습니다.
   - 수치 비교 문제: 점수가 같아서 UNDECIDED가 된 경우. **이번 FAIL 3건이 여기에 해당합니다.**
7. 크기 불일치, 라벨 `?`, expected 누락, 문자열 값, 없는 필터 크기, 파일 없음처럼 의도적으로 깨뜨린 데이터로도 실행했고, 모두 케이스 단위 FAIL 메시지만 남기고 끝까지 실행되었습니다.
8. 정책상 동점은 FAIL이 맞습니다. 이 3건을 PASS로 만들려면 동점 처리 규칙 자체를 바꿔야 하는데, 이는 과제 규칙(동점은 UNDECIDED)과 맞지 않아 그대로 두었습니다.

### 성능 분석과 시간 복잡도

측정 결과(각 크기 MAC 10회 반복 평균을 구하는 프로그램을 10번 실행해 구한 중앙값. 실행마다 조금씩 달라져 25×25는 0.023~0.036ms 범위였습니다):

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.0008 | 9 |
| 5×5 | 0.0014 | 25 |
| 13×13 | 0.0067 | 169 |
| 25×25 | 0.0249 | 625 |

9. MAC은 N×N 이중 반복문에서 칸마다 곱셈과 덧셈을 한 번씩 수행하므로 연산 횟수가 정확히 N²이고, 시간 복잡도는 **O(N²)** 입니다.
10. 3×3에서 25×25로 한 변이 약 8.3배 커지면 연산 횟수는 9에서 625로 약 69배 늘고, 측정 시간은 0.0008ms에서 0.0249ms로 약 31배 늘었습니다. 13×13에서 25×25로 갈 때는 연산 횟수가 169에서 625로 약 3.7배 늘고 시간도 0.0067ms에서 0.0249ms로 약 3.7배 늘어, 연산 횟수와 거의 정확히 비례합니다. 크기가 커질수록 시간이 선형이 아니라 이차로 증가하는 경향이 보입니다.
11. 측정 배율이 이론값(69배)보다 작은 이유는, 크기가 작을 때는 함수 호출, 반복문 시작 비용, 타이머 해상도 같은 고정 비용이 전체 시간에서 차지하는 비중이 크기 때문입니다. 크기가 커질수록 N²에 가까워집니다. 그래서 10회 반복 평균을 내고, 입출력과 JSON 파싱은 측정에서 제외했습니다.
12. 이것이 NPU가 필요한 이유입니다. 필터가 커지고 개수가 늘면 MAC 횟수는 기하급수적으로 늘고, CPU는 이를 순서대로 처리합니다. NPU는 서로 독립적인 N²번의 곱셈을 병렬로 처리해 시간을 줄입니다.

## 확장 가이드

### 새 라벨을 추가하는 절차

예를 들어 `Circle` 라벨을 추가한다고 가정합니다. 현재 코드는 표준 라벨이 `Cross`, `X` 두 가지라고 가정하고 있어서, 매핑만 넣어서는 동작하지 않고 아래 단계를 모두 거쳐야 합니다.

1. **표준 라벨 상수 추가** (`main.py` 상단): `CIRCLE = "Circle"`을 정의합니다.
2. **정규화 매핑 추가** (`LABEL_MAP`): `"o": CIRCLE`, `"circle": CIRCLE`처럼 입력 표기를 표준 라벨로 연결합니다. 이 매핑이 필터 키와 expected 양쪽에 모두 적용됩니다(`normalize_label`).
3. **필터 필수 조건 수정** (`load_filters`): 지금은 `Cross`와 `X`가 모두 있어야 로드됩니다. 필요한 라벨 목록(예: `REQUIRED_LABELS`)을 만들어 새 라벨을 포함시킵니다.
4. **판정 로직 일반화** (`judge`, `analyze_pattern`): 지금은 점수 2개를 비교하는 구조입니다. 라벨 수만큼 점수를 구해 최고점을 고르고, 최고점과 2위의 차이가 `EPSILON`보다 작으면 `UNDECIDED`로 처리하도록 바꿉니다. 출력의 "Cross 점수 / X 점수" 줄도 라벨 목록을 순회해 출력하게 바꿉니다.
5. **data.json에 등록**: `filters.size_N`에 새 라벨 키(예: `"circle": [[...]]`)를 추가하고, `patterns`에 `size_N_idx` 키로 `input`과 `expected`(새 라벨 표기)를 추가합니다.
6. **검증**: `python main.py`에서 2번을 실행해 다음을 확인합니다.
   - 새 라벨 케이스가 PASS/FAIL로 출력되고 총/통과/실패 합계가 맞는지
   - 기존 Cross/X 케이스 결과가 이전과 같은지(회귀 확인)
   - 필터와 패턴 크기를 일부러 어긋나게 한 케이스, 알 수 없는 라벨(예: `"?"`) 케이스가 중단 없이 FAIL로 처리되는지
7. **README 갱신**: 구현 요약의 라벨 표기 규칙과 결과 리포트의 케이스 수/실패 분석을 새 결과에 맞게 고칩니다.

### 대규모 입력(N ≥ 1000) 처리 시 우선 최적화

N=1000이면 한 번의 MAC이 10^6번의 곱셈과 덧셈입니다. 이 프로그램의 구현(파이썬 리스트 + 이중 반복문)으로 N=1000을 직접 재 보니 다음과 같았습니다(이 컴퓨터, 단일 실행, 참고용).

- MAC 1회: 약 42~47ms (25×25의 약 0.025ms에서 연산 횟수에 거의 비례해 늘어난 값)
- 행렬 1개의 메모리: 약 33MB (float 객체와 리스트 포인터 때문에 값 하나당 약 32바이트). 패턴과 필터 2개를 함께 올리면 약 100MB

여기서 병목은 연산 횟수보다 **메모리 사용량**과 **인터프리터 오버헤드**입니다. 필터 수천 개를 패턴마다 적용하면 시간이 필터 수에 비례해 늘고 메모리도 감당하기 어려워집니다. 우선순위는 다음과 같이 잡겠습니다.

1. **메모리 레이아웃 먼저 개선**: 2차원 리스트를 1차원 연속 버퍼로 바꿉니다(`array('d')` 또는 NumPy의 `float32`). 값 하나가 8바이트(float32는 4바이트)로 줄어 1000×1000이 약 8MB가 되고, 행 단위로 연속 접근하므로 캐시 효율도 좋아집니다. 다만 파이썬에서 `array`를 인덱스로 하나씩 읽기만 하는 방식은 빨라지지 않았고(제가 잰 값은 오히려 느렸습니다), 속도 이득은 벡터화 라이브러리나 C 구현과 함께 쓸 때 나옵니다. 이번 과제는 외부 라이브러리를 금지하므로 구현하지 않았습니다.
2. **접근 순서(스트라이드) 맞추기**: 행 우선 순서로 안쪽 반복문이 연속된 주소를 읽게 합니다. 열 우선으로 읽으면 캐시 미스가 늘어 큰 N에서 눈에 띄게 느려집니다. 지금 구현은 안쪽 반복문이 열 방향이라 행 우선 접근입니다.
3. **블록(타일) 처리**: 패턴과 필터를 예를 들어 64×64 타일로 나눠 타일 단위로 곱해 누적합니다. 한 타일이 캐시에 올라와 있는 동안 필터와 패턴을 모두 재사용하고, 부분합을 타일별로 따로 구하면 부동소수점 누적 오차도 줄어듭니다.
4. **병렬화**: 타일(또는 행 묶음)별 부분합은 서로 독립적이라 병렬로 구할 수 있습니다. 파이썬에서는 GIL 때문에 스레드가 아니라 `multiprocessing`을 쓰거나 C/NPU 같은 하드웨어에 맡겨야 합니다. 최종적으로 부분합을 모아 더하는 축약(reduce) 한 번만 순차 처리하면 됩니다. 이것이 NPU가 하는 일의 소프트웨어 버전입니다.
5. **입력 단계 최적화**: 1000×1000 JSON은 파싱만으로도 시간과 메모리를 크게 쓰므로, 한 번에 전부 로드하지 않고 스트리밍으로 읽거나 이진 형식으로 저장하는 방안을 함께 고려합니다.

정리하면 먼저 메모리 레이아웃을 바꾸고(1), 접근 순서를 맞춘 다음(2), 그래도 부족하면 타일링(3)과 병렬화(4)를 적용하는 순서가 효과 대비 비용이 가장 좋습니다.
